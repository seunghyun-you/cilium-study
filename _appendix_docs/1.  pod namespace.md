# Network Namespace 구조
네트워크 네임스페이스는 네트워크 환경을 격리하는 Linux 커널의 기능으로, 프로세스들이 독립적인 네트워크 스택을 가질 수 있게 한다. 독립적인 네트워크 스택이 구성되기 때문에 Root Network Namespace라고 해도 Pod가 할당된 Network Namespace의 정보는 직접 조회할 수 없다. 또한, 별도의 설정이 없다면 서로 다른 Network Namespace 간의 통신은 불가능하다.

## 1. Root Network Namespace
노드의 루트 네트워크 네임스페이스에 할당 된 인터페이스 정보를 조회하면 Cilium으로 인해 추가된 인터페이스와 Pod와 veth pair 구조를 이루는 인터페이스들이 같이 보인다.
- 쿠버네티스에서는 파드간의 통신, 외부와의 통신을 위해서 Pod의 Network Namespace와 Root Network Namespace를 veth pair 구조로 구성한다. 
- `xxxx@xxxx` 형식으로 보이는 인터페이스가 veth pair 구조로 생성된 인터페이스들이다.
- cilium_net과 cilium_host는 모두 Root Network Namespace에 구성된 인터페이스이기 때문에 2개의 pair 인터페이스가 동시에 조회된다.
- 반면, `lxc_xxx...`  형식으로 구성된 인터페이스는 파드의 veth pair 구조로 구성된 인터페이스(`ifxx`)다. 다른 Network Namespace에 할당되어 있기 때문에 정보가 조회되지 않는다.

```bash
root@cilium-ctr:~# ip -br -c a
lo               UNKNOWN        127.0.0.1/8 ::1/128 
eth0             UP             10.0.2.15/24 metric 100 fd17:625c:f037:2:a00:27ff:fe6b:69c9/64 fe80::a00:27ff:fe6b:69c9/64 
eth1             UP             192.168.10.100/24 fe80::a00:27ff:fe6d:4a81/64 
cilium_net@cilium_host UP       fe80::dc9e:50ff:fe18:1a3/64 
cilium_host@cilium_net UP       172.20.0.115/32 fe80::a473:b9ff:fe8d:cd55/64 
lxc_health@if6   UP             fe80::507b:4bff:fef1:f98d/64 
lxc25acf64997d3@if8 UP          fe80::9c24:e5ff:fe27:f6d3/64 
lxce7ac95c06973@if10 UP         fe80::b49a:5dff:fe39:8923/64 
lxccfed039b965e@if12 UP         fe80::8c94:c7ff:fece:3aae/64 
lxc51def2d28240@if14 UP         fe80::4872:5eff:fea2:3827/64 
lxcdf4324a1c738@if16 UP         fe80::84ff:45ff:fe12:5104/64 
```

## 2. ip link 정보 
`ip link` 명령으로 파드와 pair 구조로 구성된 인터페이스의 정보를 보면 각 인터페이스가 어떤 Network Namespace에 구성되었는지 볼 수 있다.
- netnsid 0는 Root Network Namespace를 의미한다.
- link-netns <NAMESPACE_NAME> 은 파드가 할당 된 Network Namespace 정보가 표시된다.

# Pod Network Namespace
파드가 배포되어 있는 노드의 `/run/netns` 디렉터리를 조회하면 파드를 위해 생성된 네트워크 네임스페이스 정보를 확인할 수 있다. 이 곳의 폴더 이름만 보면 어떤 파드에 맵핑된 네임스페이스 인지 확인하기 어렵다. 파드의 네임스페이스 정보를 확인하기 위해서는 파드의 PID 정보를 이용해서 네임스페이스의 inode 정보를 확인해야 한다.

```bash
root@cilium-ctr:~# ls -l /run/netns
total 0
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-090b3a63-8f29-11a7-559b-366b1a92a624
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-b3ebe539-cfb6-b9e6-3f2a-a1af09ecbea3
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-dd77827c-0ad3-1d6d-ad48-21e626a096a9
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-f7309b13-99f1-da3e-ea8a-1619433cb3b6
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-f84067f7-b39b-5d04-6733-afc6d80c7548
```

> [!NOTE]
> **/run/netns 정보**
> - Pod (Container)가 생성되면 Network 격리를 위한 별도의 네트워크 네임스페이스를 만들고 그 정보를  `/run/netns` 디렉터리에 저장한다.
> - `/run/netns`는 `ip netns add` 명령어를 통해 명시적으로 생성된 Network Namespace의 정보가 저장되는 디렉터리다.
> - Network Namespace의 정보는 `lsns` 명령을 이용할 수도 있다.

## Pod에 할당된 Namespaces 정보 조회

### 1. Pod에 할당된 container ID 조회
```bash
# kubectl get po <pod-name> -n kube-system -o=jsonpath='{.status.containerStatuses[0].containerID}'
root@cilium-ctr:~# kubectl get po curl-pod-01 -n default -o=jsonpath='{.status.containerStatuses[0].containerID}'
containerd://afac84b2f299af7cdc6c9ecf90fc0773e9517d43b2e7b53bdb4032749cdc9543
```

### 2. container id로 할당된 PID 정보 조회
```bash
# docker : docker inspect -f '{{.State.Pid}}' <container-id>
# containerd  : crictl inspect --output json <container-id> | jq .info.pid
root@cilium-ctr:~# crictl inspect --output json afac84b2f299af7cdc6c9ecf90fc0773e9517d43b2e7b53bdb4032749cdc9543 | jq .info.pid
3043
```

### 3. PID에 할당된 Network Namespace inode 정보 조회
```bash
#ls -l /proc/<PID>/ns/net
root@cilium-ctr:~# ls -l /proc/3043/ns/net
lrwxrwxrwx 1 root root 0 Nov 24 18:28 /proc/3043/ns/net -> 'net:[4026532760]'
```

### 4. Network Namespace inode 이용 Network Namespace 이름 조회
```bash
root@cilium-ctr:~# ls -i /run/netns | grep 4026532760
4026532760 cni-090b3a63-8f29-11a7-559b-366b1a92a624
```

### 5. Namespace에 할당된 IP 정보 조회
```bash
root@cilium-ctr:~# ip netns exec cni-090b3a63-8f29-11a7-559b-366b1a92a624 ip -c -br a
lo               UNKNOWN        127.0.0.1/8 ::1/128 
eth0@if17        UP             172.20.0.92/32 fe80::c05c:55ff:fed8:4671/64 
```

## Network Namespace와 veth pair 생성 예제

### 1. Namespace 생성

```bash
root@cilium-ctr:~# ip netns add ns1
root@cilium-ctr:~# ls -l /run/netns
total 0
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-090b3a63-8f29-11a7-559b-366b1a92a624
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-b3ebe539-cfb6-b9e6-3f2a-a1af09ecbea3
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-dd77827c-0ad3-1d6d-ad48-21e626a096a9
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-f7309b13-99f1-da3e-ea8a-1619433cb3b6
-r--r--r-- 1 root root 0 Nov 24 16:02 cni-f84067f7-b39b-5d04-6733-afc6d80c7548
-r--r--r-- 1 root root 0 Nov 24 23:37 ns1
```

### 2. veth pair 생성

```bash
root@cilium-ctr:~# ip -br a | grep veth
veth1@veth0      DOWN           
veth0@veth1      DOWN      
```

### 3. veth0 인터페이스의 Network Namespace 변경
인터페이스가 할당된 Network Namespace 정보를 변경하고 나면 Root Network Namespace에서는 그 정보가 조회되지 않는다.
```bash
root@cilium-ctr:~# ip link set veth0 netns ns1
root@cilium-ctr:~# ip -br a | grep veth
veth1@if19       DOWN      
```

### 4. veth pair에 IP 할당 후 통신 테스트
```bash
root@cilium-ctr:~# ip netns exec ns1 ifconfig veth0 192.168.1.1/24 up
root@cilium-ctr:~# ifconfig veth1 192.168.1.2/24 up
root@cilium-ctr:~# ping 192.168.1.1
PING 192.168.1.1 (192.168.1.1) 56(84) bytes of data.
64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=0.088 ms
64 bytes from 192.168.1.1: icmp_seq=2 ttl=64 time=0.062 ms    
```

### 5. Network Namespace 삭제
```bash
root@cilium-ctr:~# ip netns delete ns1
```
